# Manner_Web 后端开发指南

> 面向后端开发者的工程指南：技术栈与依赖、项目结构、配置项、本地开发、代码规范、测试与验证，以及「新增一个受权限保护的端点」的完整步骤。
>
> 本指南描述的目录、路由、表与权限均以当前代码为准（`backend/src/`、`backend/sql/init.sql`）。系统设计与安全背景见 [`架构设计.md`](架构设计.md)、[`API文档.md`](API文档.md)、[`权限系统设计.md`](权限系统设计.md)。

| 类别 | 选型 |
| --- | --- |

```

├── Cargo.toml
├── .env.example          # 仅 8 个核心配置项（见第 3 节）

│   └── init.sql          # 建表 + 种子数据（启动时自动迁移，见下）
```

## 3. 配置项

全部环境变量由 `backend/src/config.rs` 的 `Config::from_env()` 读取：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DATABASE_URL` | 必填，无默认 | MySQL 连接串，如 `mysql://user:pass@host:3306/manner_web` |
| `JWT_SECRET` | 无默认（若为公开默认值**直接 panic 拒绝启动**） | HS256 签名密钥；长度 <32 时启动告警；建议 ≥64 随机字符 |
| `BCRYPT_COST` | 12 | bcrypt 成本 |
| `TOKEN_EXPIRE_MINUTES` | 30 | access 令牌有效期（分钟） |
| `REFRESH_TOKEN_EXPIRE_DAYS` | 7 | refresh 令牌有效期（天） |
| `LOG_LEVEL` | debug | 日志级别（`RUST_LOG` 优先） |
| `SERVER_HOST` | 127.0.0.1 | 绑定 0.0.0.0 会告警 |
| `SERVER_PORT` | 8080 | 监听端口 |
| `UPLOAD_DIR` | ./uploads | 上传目录 |
| `LOG_FILE` | ./logs/manner.log | 业务日志文件（`GET /api/system/logs` 读取展示） |
| `CORS_ALLOWED_ORIGINS` | http://localhost:5173,http://127.0.0.1:5173 | 逗号分隔白名单；含 `*` 告警 |
| `LOGIN_MAX_FAILURES` | 5 | 登录限流阈值（`system_settings` 可覆盖） |
| `LOGIN_LOCK_WINDOW_SECS` | 900 | 限流窗口秒数（`system_settings` 可覆盖） |
| `COOKIE_SECURE` | false | 非本机绑定且未开启时告警；生产 HTTPS 下必须 `true` |
| `PROFILE` | — | 由 `main.rs` 读取（非 Config 字段）：`production` 时启用 JSON 滚动日志（`logs/manner.log` 每日滚动），否则终端格式 |

> `backend/.env.example` 只列了 8 个核心项（`DATABASE_URL`、`JWT_SECRET`、`BCRYPT_COST`、`TOKEN_EXPIRE_MINUTES`、`LOG_LEVEL`、`SERVER_HOST`、`SERVER_PORT`、`CORS_ALLOWED_ORIGINS`），其余变量均有默认值，无需在 `.env` 中显式配置。`.env` 文件不入库。

## 4. 本地开发

### 4.1 准备 MySQL

需 MySQL 8 实例，创建数据库与账号（utf8mb4，与应用一致）：

```sql
CREATE DATABASE manner_web CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'manner'@'localhost' IDENTIFIED BY 'your-strong-password';
GRANT ALL PRIVILEGES ON manner_web.* TO 'manner'@'localhost';
FLUSH PRIVILEGES;
```

表结构不需要手工导入：后端启动时 `run_migrations` 会按 `;` 分割 `backend/sql/init.sql` 逐条执行（跳过 `CREATE DATABASE` / `USE` 语句；语句失败仅告警不中断；幂等，可重复启动）。建表语句以 `backend/sql/init.sql` 为准，表结构说明见 [`数据库设计.md`](数据库设计.md)。

### 4.2 配置 .env

```bash
cd backend
cp .env.example .env
```

编辑 `.env`，至少填写：

```dotenv
DATABASE_URL=mysql://manner:your-strong-password@127.0.0.1:3306/manner_web
JWT_SECRET=<至少 32 位随机字符串，建议 64 位>
```

### 4.3 启动后端

```bash
cd backend
cargo run
```

启动顺序（`main.rs`）：读取配置 → 初始化日志 → 输出安全配置告警（如 `JWT_SECRET` 过短、绑定 0.0.0.0 等）→ 连接池 → 执行迁移 → 生成登录防枚举假 bcrypt 哈希 → 构造限流器 → 装配路由 → 监听 `127.0.0.1:8080`。看到 `Server starting on 127.0.0.1:8080` 即就绪。

开发时启动前端（可选，联调用）：

```bash
cd frontend
npm install
npm run dev   # Vite Dev Server :5173，代理 /api、/uploads → http://localhost:8080
```

### 4.4 创建首个管理员

全新部署（`employees` 表为空且 `registration_open='1'`）时，通过注册接口创建首个管理员：

```bash
curl -X POST http://localhost:8080/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","name":"管理员","password":"your-password-here"}'
```

或直接在浏览器打开 `http://localhost:5173/login` 走注册页。机制要点：

- 条件：`system_settings.registration_open='1'` 且 `employees` 表无任何记录；事务内 `SELECT … FOR UPDATE` 防并发抢注。
- 成功注册后自动给该员工授予**全部权限**，并将 `registration_open` 置为 `'0'`；此后注册接口一律 403。
- 该账号即为**首个管理员**，建议在「员工管理」中为其开启防拉黑保护（`protect_block=1`），防止被误删/误拉黑。

## 5. 代码规范

### 5.1 错误处理：AppError

所有 handler 返回 `Result<Json<ApiResponse<T>>, AppError>`，错误经 `backend/src/error.rs` 的 `IntoResponse` 统一映射为 `{code, message, data:null}`，**不要在 handler 里手工拼错误 JSON**。

```rust
use axum::extract::{Path, State};
use axum::Json;

use crate::error::AppError;
use crate::middleware::auth::{require_permission, AppState, AuthUser};
use crate::models::employee::EmployeeDetail;
use crate::utils::response::ApiResponse;

pub async fn get_employee(
    State(state): State<AppState>,
    auth: AuthUser,
    Path(id): Path<String>,
) -> Result<Json<ApiResponse<EmployeeDetail>>, AppError> {
    require_permission(&auth.permissions, "employee:view")?;

    let row = sqlx::query_as::<_, EmployeeDetailRow>(
        "SELECT e.id, e.username, e.name, e.title, e.avatar, e.status, e.protect_block \
         FROM employees e WHERE e.id = ?",
    )
    .bind(&id)
    .fetch_optional(&state.pool)
    .await?
    .ok_or(AppError::NotFound)?;

    Ok(Json(ApiResponse::ok(EmployeeDetail { /* ... */ })))
}
```

常用错误变体与 HTTP 映射（完整错误码表见 [`架构设计.md`](架构设计.md) 第 2 节）：

| 变体 | HTTP | code | 典型场景 |
| --- | --- | --- | --- |
| `AppError::BadRequest(msg)` | 400 | 40000 | 参数不合法，如「文件上传已被管理员禁止」 |
| `AppError::ValidationError(msg)` | 400 | 40005 | 字段校验失败 |
| `AppError::NotFound` | 404 | 40006 | 资源不存在 |
| `AppError::Conflict` | 409 | 40007 | 用户名已存在 |
| `AppError::Forbidden` | 403 | 40004 | 无权限（由 `require_permission` 返回） |
| `AppError::Internal(anyhow!(e))` | 500 | 50000 | 服务器内部错误（`sqlx::Error` 已自动 `From` 转换并记录日志） |

### 5.2 权限校验：require_permission

受权限保护的端点，在 handler 第一行校验权限（`AuthUser` 已由 `auth_middleware` 注入，权限码取自 access 令牌）：

```rust
require_permission(&auth.permissions, "employee:create")?;  // 无权限 → 403 (40004)
```

- 仅需登录的端点（如聊天会话接口）不调用 `require_permission`，由路由层 `auth_middleware` 兜底。
- 权限码清单（11 个）见 [`权限系统设计.md`](权限系统设计.md)；middleware 中只有 `require_permission`，没有部门/数据范围类校验函数。

### 5.3 上传统一复用 save_upload

所有上传落盘逻辑统一由 `backend/src/handlers/system.rs` 的 `save_upload(state, auth, multipart, image_only)` 实现（`POST /api/upload` 与 `POST /api/upload/file` 均复用它），包含：`chat_upload_limit` 限制检查、扩展名校验、图片魔数校验、UUID 重命名、`uploads/chat/` 子目录隔离、业务日志与统一错误。**新增上传入口直接复用该函数（必要时将其提升为 `pub`），不要在业务模块里另写落盘逻辑**，否则会绕过魔数校验与子目录隔离等安全约束。

### 5.4 业务日志：append_log

关键业务事件（上传成功/失败、权限变更、设置变更等）用 `handlers/auth.rs` 导出的 `append_log` 写入 `LOG_FILE`：

```rust
use crate::handlers::auth::{append_log, user_tag};

append_log(
    &state.config.log_file,
    &format!("用户 {} 更新员工 {} 权限", user_tag(&auth.name, &auth.username), target_name),
);
```

日志文件由 `GET /api/system/logs`（需 `system:settings`）在线查看。

### 5.5 客户端 IP 取 TCP 对端

客户端 IP 一律取 TCP 对端地址，**不信任 `X-Forwarded-For`**（限流与审计用）：

```rust
use axum::extract::ConnectInfo;
use std::net::SocketAddr;

pub async fn some_handler(
    State(state): State<AppState>,
    auth: AuthUser,
    ConnectInfo(addr): ConnectInfo<SocketAddr>,
) -> Result<Json<ApiResponse<()>>, AppError> {
    let client_ip = addr.ip().to_string();
    // ...
}
```

该提取器依赖 `main.rs` 中以 `into_make_service_with_connect_info::<SocketAddr>()` 启动服务（已就位，勿移除）。

### 5.6 数据库访问与事务

- 连接池：通过 `State(state): State<AppState>` 取 `state.pool`（sqlx `MySqlPool`），不要自行新建连接。
- SQL 一律用运行时查询 + `bind` 参数化（`query` / `query_as` / `query_scalar`），禁止字符串拼接。
- 多语句写操作用事务：

```rust
let mut tx = state.pool.begin().await?;
sqlx::query("UPDATE employees SET status = ? WHERE id = ?")
    .bind(new_status)
    .bind(&id)
    .execute(&mut *tx)
    .await?;
tx.commit().await?;
```

参考实现：`handlers/auth.rs::register`（`SELECT … FOR UPDATE` 防并发抢注）、`handlers/employee.rs::update_employee_permissions`（DELETE 全量重插）。

## 7. 常见任务示例：新增一个受权限保护的端点

以「新增 `PUT /api/announcements/:id`（编辑公告，权限码 `announcement:edit`，归属 system 模块）」为例：

| 步骤 | 操作 | 说明 |
| --- | --- | --- |
| 1 | 注册路由 | 在 `backend/src/handlers/mod.rs` 的 `protected_routes` 中加 `.route("/api/announcements/:id", put(system::update_announcement))`（`protected_routes` 整体已叠加 `auth_middleware`） |
| 2 | 编写 handler | 在 `handlers/system.rs`（或按模块新建 `handlers/announcement.rs`）实现 handler（见下方模板） |
| 3 | 定义结构体 | 在 `backend/src/models/employee.rs` 增加请求/响应结构体（`UpdateAnnouncementRequest` 等），字段全部用 `Option` 表示可选 |
| 4 | 添加权限码种子 | 在 `backend/sql/init.sql` 的 permissions 种子区加 `INSERT IGNORE INTO permissions (code, name, module) VALUES ('announcement:edit', '编辑公告', 'system');`（迁移幂等，重启后生效） |
| 5 | 补充授权 | 已注册的账号（含首个管理员）不会自动获得新权限码：在「员工管理 → 权限分配」中为新码打勾（走 `PUT /api/employees/:id/permissions`，受子集约束），或对首个管理员执行 `INSERT IGNORE INTO employee_permissions (employee_id, permission_id) SELECT e.id, p.id FROM employees e, permissions p WHERE e.username='admin' AND p.code='announcement:edit';`。全新部署时首个管理员注册仍会自动获得全部权限 |
| 6 | 同步前端 | `frontend/src/lib/types/index.ts` 增加 `UpdateAnnouncementRequest` 类型；`frontend/src/lib/api/system.ts` 增加 `updateAnnouncement(id, body)` 调用 `client.put` |
| 7 | 验证 | 见下方验证清单 |

Handler 模板（与 `handlers/system.rs` 同风格）：

```rust
use axum::extract::{Path, State};
use axum::Json;
use serde::Deserialize;

use crate::error::AppError;
use crate::middleware::auth::{require_permission, AppState, AuthUser};
use crate::utils::response::ApiResponse;

#[derive(Debug, Deserialize)]
pub struct UpdateAnnouncementRequest {
    pub title: Option<String>,
    pub content: Option<String>,
}

pub async fn update_announcement(
    State(state): State<AppState>,
    auth: AuthUser,
    Path(id): Path<String>,
    Json(body): Json<UpdateAnnouncementRequest>,
) -> Result<Json<ApiResponse<()>>, AppError> {
    require_permission(&auth.permissions, "announcement:edit")?;

    // 校验资源存在，避免「更新 0 行」被当作成功
    let exists = sqlx::query_scalar::<_, i64>(
        "SELECT COUNT(*) FROM announcements WHERE id = ?",
    )
    .bind(&id)
    .fetch_one(&state.pool)
    .await?;
    if exists == 0 {
        return Err(AppError::NotFound);
    }

    if let Some(title) = body.title {
        sqlx::query("UPDATE announcements SET title = ? WHERE id = ?")
            .bind(title)
            .bind(&id)
            .execute(&state.pool)
            .await?;
    }
    // ... content 同理；审计日志：
    // append_log(&state.config.log_file, &format!("用户 {} 更新公告 {}", user_tag(&auth.name, &auth.username), id));

    Ok(Json(ApiResponse::ok_msg("保存成功")))
}
```

验证清单：

| 场景 | 期望 |
| --- | --- |
| 未登录调用 | 401，`code=40002`（`auth_middleware` 拦截） |
| 已登录但无 `announcement:edit` 权限 | 403，`code=40004`（`require_permission`） |
| 有权限 + 合法参数 | 200，`code=0`，`message="保存成功"` |
| 有权限 + 资源不存在 | 404，`code=40006` |
| 参数缺失/类型错误 | 400，`code=40000`（422/文本 400 由 `harden_response_middleware` 收敛） |

> **权限模型说明**：角色机制已移除，**新增权限一律走员工级直接授权**（`employee_permissions` 表），不存在角色绑定步骤；新权限码加到 `init.sql` 种子后，已注册账号需在员工管理中手动勾选授权。
