# Manner_Web 加密与安全标准

> 适用范围：开发与维护人员。
> 事实依据：`backend/src/services/auth.rs`（bcrypt 与初始密码）、`backend/src/handlers/auth.rs`（登录/注册/改密/令牌签发）、`backend/src/utils/jwt.rs`（Claims 与令牌）、`backend/src/middleware/auth.rs`（校验链）、`backend/src/middleware/security.rs` 与 `backend/src/middleware/strip_allow.rs`（响应头与收敛）、`backend/src/handlers/system.rs` 与 `backend/src/handlers/mod.rs`（上传与静态目录守卫）、`backend/src/config.rs`（环境变量与告警）。以代码为准。

## 1. 密码存储

| 项目 | 标准 |
| --- | --- |
| 算法 | bcrypt（`bcrypt` crate 0.16），成本 `BCRYPT_COST` 默认 **12** |
| 盐 | 每次哈希随机盐；存储只含哈希，**不保存明文** |
| 校验 | `verify_password` 对 bcrypt 校验异常（空哈希/非法哈希等）一律返回 `false`，不区分错误 |
| 兼容性 | 无任何客户端预哈希兼容逻辑，存储格式统一为服务端 `bcrypt(明文)` |

**防枚举配套**：

- 启动时按 `BCRYPT_COST` 生成一个等开销的固定假哈希 `login_dummy_hash`；
- 登录「用户名不存在」分支执行一次等开销假校验，使「用户名不存在」与「密码错误」两条失败路径耗时一致，消除时序侧信道；
- `precheck` 的假校验统一在 SQL 查询之前执行；
- 登录/预检/首登失败统一返回 40001「用户名或密码错误」，不区分账号不存在/禁用。

**初始密码**：创建员工时由 `generate_random_password()` 生成 **16 位字母数字**密码（约 95 bit 熵），仅在创建响应中返回一次；同时置 `must_change_password = 1`，强制首次登录改密（流程见 `SECURITY.md`）。新密码/改密密码至少 8 位。

## 2. 密码传输

- 登录（`POST /api/auth/login`）、首登激活（`POST /api/auth/first-login`）、改密（`PUT /api/auth/password`）均以 **HTTPS 明文 POST** 传输密码（JSON 字段）。
- 前端**不做预哈希**，理由：
  1. 传输层负责保密——生产全站 HTTPS，明文仅在 TLS 通道内出现（部署模板见 `nginx-prod.conf.example`）；
  2. 服务端需要明文做 bcrypt 校验与重新哈希（改密时），客户端预哈希无法满足「服务端只存 `bcrypt(明文)`」的约束；
  3. 密码学方案不应在客户端固定（更换算法/加盐策略将无法兼容旧客户端）；
  4. 浏览器端 JS 密码学（WebCrypto）能力受限且易被 XSS 窃取，密钥管理在浏览器内不可靠。
- **生产要求**：全站 HTTPS（Nginx 强制 80→443 跳转，模板见 `nginx-prod.conf.example`）；开发环境仅限本机回环。

## 3. JWT 令牌

### 3.1 算法与密钥

- 算法 **HS256**（`jsonwebtoken` 9），对称密钥 `JWT_SECRET`。
- `JWT_SECRET` 要求：
  - **无默认值**：代码中虽存在公开默认值，但检测到使用默认值会直接 `panic` 拒绝启动（「JWT_SECRET 仍为公开默认值，拒绝启动」）；
  - 长度 **≥ 32**（低于 32 启动时输出 `security_warnings` 告警），**建议 ≥ 64** 随机值；
  - **更换即全端失效**：JWT 为无状态签名，更换密钥后所有已签发令牌立即验签失败，需重启服务后全员重新登录。

### 3.2 双令牌

| 令牌 | Cookie | 有效期 | 内容 |
| --- | --- | --- | --- |
| access | `manner_token` | `TOKEN_EXPIRE_MINUTES`（默认 30 分钟） | `typ=access`，内嵌 `permissions` 权限快照 |
| refresh | `manner_refresh` | `REFRESH_TOKEN_EXPIRE_DAYS`（默认 7 天） | `typ=refresh`，**不携带 permissions**，仅 `POST /api/auth/refresh` 可用 |

Claims：`sub`（员工 id）、`username`、`name`、`permissions`、`exp`、`jti`、`pwd_version`、`typ`。

### 3.3 失效机制

| 场景 | 机制 |
| --- | --- |
| 登出 | access 与 refresh 的 `jti` **同时**写入 `token_blacklist`，并下发 `Max-Age=0` 清除双 Cookie |
| refresh 轮换 | 每次用 refresh 换新时，旧 refresh 的 `jti` 立即入黑名单（旧令牌不可再次续期） |
| 改密/重置/首登激活 | `pwd_version` 递增 → 全端踢出（所有已签发 access/refresh 立即失效） |
| 账号禁用 | `status != 1` → 已签发令牌立即失效 |

### 3.4 校验链（中间件，以代码为准）

```
取 token（Authorization: Bearer 或 Cookie manner_token）
→ 验签（HS256）
→ typ 必须为 "access"（refresh 冒充 access 拒绝）
→ jti 不在 token_blacklist
→ 员工存在且 pwd_version 与库一致且 status = 1
→ 通过
```

## 4. Cookie 安全属性

| 属性 | 值 | 说明 |
| --- | --- | --- |
| HttpOnly | 是 | 前端 JS 不可读，消除 XSS 窃取面（JWT 不落 localStorage） |
| SameSite | Strict | 跨站请求不携带 Cookie，**CSRF 免疫**（依赖同站语义，见 `SECURITY.md` 权衡） |
| Path | / | 全站生效 |
| Secure | `COOKIE_SECURE` | 生产 HTTPS 必须 `true`；非本机绑定且未开启时启动输出告警 |
| Max-Age | 令牌有效期 | 登出时置 0 清除 |

## 5. 上传文件安全

### 5.1 两个上传端点

| 端点 | 权限 | 用途 | 行为 |
| --- | --- | --- | --- |
| `POST /api/upload` | 仅登录 | 图片（头像等） | 扩展名白名单 + 魔数校验；存 `UPLOAD_DIR` 根目录；返回 `/uploads/{uuid}.{ext}` |
| `POST /api/upload/file` | `chat:upload` | 任意文件（聊天附件） | ASCII 字母数字扩展名（非空、≤16 字符）；图片类仍魔数校验；存 `UPLOAD_DIR/chat/` 子目录；返回 `/uploads/chat/{uuid}.{ext}` |

公共限制：受系统设置 `chat_upload_limit` 限制（"禁止" → 拒绝；"无限制" → 不限；数字+单位 B/KB/MB/GB/TB）；`DefaultBodyLimit` **100MB** 硬限制。

### 5.2 校验与存储

- **图片白名单**：png/jpg/jpeg/gif/webp/bmp/ico（刻意排除 svg/html/xml 等可携带脚本的类型，防存储型 XSS）。
- **魔数校验**：PNG `89504E47`、JPEG `FFD8FF`、GIF `GIF8`、WEBP `RIFF…WEBP`、BMP `BM`、ICO `00000100`；不符返回 400「文件内容与声明类型不符」。
- **UUID 重命名**：落盘名为 `{uuid}.{ext}`，原始文件名不落盘。
- **任意文件扩展名白名单**：仅 ASCII 字母数字、非空、≤16 字符（防路径混淆）。

### 5.3 访问控制

- **聊天文件隔离**：聊天文件一律存 `uploads/chat/` 子目录；`/uploads/chat/*` 静态访问**一律 404**，只能经 `GET /api/chat/file/:name` 下载。
- **聊天文件下载三重校验**（`chat.rs::get_chat_file`）：
  1. 文件名白名单（ASCII 字母数字 + `.` + `-`，≤64，禁 `..` 与前导点）+ 扩展名合法；
  2. 文件必须被某条消息引用（`file_url` 匹配 `/uploads/chat/<name>` 或存量 `/uploads/<name>`），未被引用的文件不可读；
  3. 当前用户必须是相关会话的成员（否则 403）；读取前检查软链接（任一候选路径为软链接 → 404）。
  图片内联返回，其余强制 `Content-Disposition: attachment`。
- **`/uploads` 静态守卫**（`uploads_extension_guard` + `auth_middleware`）：
  - 需登录（Bearer 或 HttpOnly Cookie，未登录 401）；
  - 扩展名为空 → 403；路径任一级为软链接 → 404；文件未被 `employees.avatar` 或 `messages.file_url` 引用 → 404；
  - 图片扩展名内联，**非图片强制 `attachment`**（即使上传了 html/svg 等也不被浏览器执行，配合全局 nosniff 双重兜底）。
- **文件消息校验**（发送消息时）：文件消息必须携带 `file_url`（否则 400）；`file_url` 必须以 `/uploads/` 开头且扩展名合法（否则 400「文件链接必须指向本站上传的文件」）；`file_name` 超过 256 字符 → 400。

## 6. 安全响应头与响应面收敛

### 6.1 响应头（后端 harden 中间件统一下发）

| 头 | 值 |
| --- | --- |
| X-Content-Type-Options | nosniff |
| X-Frame-Options | DENY |
| Strict-Transport-Security | max-age=31536000; includeSubDomains |
| Referrer-Policy | no-referrer |
| x-permitted-cross-domain-policies | none |

后端**不输出 CSP 与自定义 Server 头**：CSP 与 Server 头由前端 dev server（开发）与生产 Nginx（`nginx-prod.conf.example`，含 CSP、Permissions-Policy、`server_tokens off`）负责。

### 6.2 其他收敛

| 项目 | 机制 |
| --- | --- |
| Allow 头剥离 | `StripAllowMakeService`（最外层）剥离所有响应 `Allow` 头 |
| 422 / 文本 400 / 415 收敛 | harden 中间件统一替换为 40000 通用参数错误（JSON），避免泄露 serde 字段名与技术栈指纹 |
| 未知路由 | 统一 fallback 401（code=40002），消除已注册/未注册路径的响应码差分 |
| CORS | 白名单（`CORS_ALLOWED_ORIGINS`）+ `allow_credentials(true)`；方法 GET/POST/PUT/DELETE/OPTIONS；头 Content-Type/Accept/Authorization；含 `*` 启动告警 |

## 7. 凭据管理

- `.env` **不入库**：仓库只提供 `backend/.env.example`（8 个核心项占位），实际密钥由运维在部署机维护。
- 生产配置通过**环境变量注入**（systemd `Environment=` / Docker `-e` / K8s Secret），见 `../README.md` 部署章节。
- 生产最小配置：`DATABASE_URL`、强随机 `JWT_SECRET`（≥32，建议 ≥64）、`COOKIE_SECURE=true`、`CORS_ALLOWED_ORIGINS=https://<your-domain>`、`SERVER_HOST=127.0.0.1`、`LOG_LEVEL=info`、`PROFILE=production`。
- **密钥轮换建议**：定期更换 `JWT_SECRET`（更换即全端踢出，安排在低峰期）；数据库口令遵循最小权限与定期轮换；初始密码交付后强制首登改密，不通过明文渠道二次传递。
- 启动时检查 `security_warnings` 日志，无告警再对外暴露（详见 `SECURITY.md` 配置安全）。
