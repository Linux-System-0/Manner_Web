# Manner_Web 权限系统设计

> 适用范围：开发与维护人员。
> 事实依据：`backend/sql/init.sql`（权限码种子）、`backend/src/handlers/auth.rs`（首个管理员注册与令牌签发）、`backend/src/handlers/employee.rs`（权限分配操作）、`backend/src/handlers/chat.rs`（防拉黑保护）、`backend/src/middleware/auth.rs`（校验与 `require_permission`）、`backend/src/utils/jwt.rs`（Claims）。以代码为准。

## 1. 权限模型总览

系统采用 **员工级直接授权** 单一路径，**RBAC 角色机制已移除**（无 `roles` / `employee_roles` / `role_permissions` / `role_department_scopes` 表，无部门数据范围，无 `is_unrestricted` / `department_ids` claim）：

```
employees ──employee_permissions──► permissions
```

- **最终权限** = 该员工在 `employee_permissions` 中被直接授予的全部权限码的并集（单一路径下即该集合本身）。
- **令牌快照**：签发 access 令牌时查库取出员工全部权限码（`SELECT p.code FROM permissions p INNER JOIN employee_permissions ep ...`）并内嵌到 JWT 的 `permissions` claim。此后权限变更不会立即反映到已签发令牌：需**重新登录**，或等待令牌过期（默认 30 分钟）后经 refresh 自动换发——换发时由服务端重新查库取最新权限（见 `加密标准.md`）。
- 权限检查基于 **权限码**（字符串，如 `employee:list`），由 `require_permission` 比对令牌内权限快照完成，不涉及任何角色或部门范围概念。

## 2. 权限码清单（11 个）

种子数据位于 `backend/sql/init.sql`（`INSERT IGNORE INTO permissions`）。按模块分组：

### 2.1 员工模块（employee）

| code | 名称 | 说明 |
| --- | --- | --- |
| employee:list | 查看员工列表 | 访问员工列表与权限字典（`GET /api/employees`、`GET /api/permissions`） |
| employee:view | 查看员工详情 | 查看单个员工详情（`GET /api/employees/:id`） |
| employee:create | 新增员工 | 创建员工账号（`POST /api/employees`） |
| employee:edit | 编辑员工 | 编辑员工资料、修改他人权限（`PUT /api/employees/:id`、`PUT /api/employees/:id/permissions`） |
| employee:delete | 删除员工 | 删除员工账号（`DELETE /api/employees/:id`） |
| employee:password | 重置员工密码 | 重置他人密码（`PUT /api/employees/:id/password`，不可重置自己） |

### 2.2 聊天模块（chat）

| code | 名称 | 说明 |
| --- | --- | --- |
| chat:protect_block | 防拉黑保护 | 权限矩阵勾选即置位员工 `protect_block=1`（受保护） |
| chat:group_create | 群聊创建 | 创建群聊（`POST /api/chat/conversations`；校验：持有 `chat:group_create` 权限） |
| chat:upload | 上传文件 | 上传任意聊天文件（`POST /api/upload/file`） |

### 2.3 系统模块（system）

| code | 名称 | 说明 |
| --- | --- | --- |
| system:settings | 系统设置 | 系统设置、健康检查与日志（`GET/PUT /api/system/settings`、`GET /api/system/health`、`GET /api/system/logs`） |
| system:config | 系统配置 | 种子保留码，当前无端点校验 |

> **种子保留码**：`system:config` 存在于权限种子表，但当前没有任何端点校验，仅随「首个管理员授全部权限」一并授予，供后续功能扩展使用。

## 3. 首个管理员

系统不提供「创建管理员」管理接口，首个管理员通过**匿名注册**创建（`POST /api/auth/register`）：

| 条件 | 说明 |
| --- | --- |
| 注册开关 | `system_settings.registration_open = '1'`（全新部署默认） |
| 员工数 | `employees` 表无任何记录（员工数 = 0） |
| 并发防护 | 事务内 `SELECT ... FOR UPDATE` 锁定注册开关，防止并发抢注出多个管理员 |
| 成功效果 | 自动授予**全部权限**（`INSERT ... SELECT id FROM permissions`），并将 `registration_open` 置 `'0'` |

已有任意账号后注册一律返回 403（注册通道关闭）。匿名注册入口仅存在于全新部署首次启动后的窗口期。

## 4. 授权操作：PUT /api/employees/:id/permissions

权限分配是**覆盖式**的，规则如下：

| 规则 | 说明 |
| --- | --- |
| 所需权限 | 操作者须持有 `employee:edit`，否则 403（code=40004） |
| 覆盖式写入 | 事务内先 `DELETE FROM employee_permissions WHERE employee_id = ?` 全量删除，再按请求中的 `permission_codes` 重新插入 |
| 子集约束（防提权） | 请求中的每个权限码都必须是**操作者自身权限的子集**，否则 403（受限管理员无法授予自己没有的权限，如 `system:config`） |
| 不能改自己 | 目标为自己时 400「不能修改自己的权限」 |
| 目标不存在 | 404（资源不存在） |

授权后目标员工的**已签发令牌不受影响**（令牌内权限为签发时快照），其新权限在重新登录或令牌过期自动刷新后生效。

## 5. 防拉黑保护（protect_block）

- **标记**：`employees.protect_block`（员工级布尔标记，TINYINT 0/1）。
- **置位**：权限矩阵中勾选 `chat:protect_block` 权限即置位 `protect_block=1`（员工受保护），取消勾选即取消防拉黑保护——由 `PUT /api/employees/:id/permissions`（`update_employee_permissions`）保存权限时联动，无独立置位接口。
- **语义**：`protect_block = 1` 仅表示该员工**不可被他人拉黑**（拉黑接口返回 400「该用户受保护，无法拉黑」），对删除、改资料、重置密码、修改权限等管理操作**无影响**。

保护标记仅用于聊天侧的防拉黑兜底，管理操作由对应权限码（`employee:delete`、`employee:edit`、`employee:password` 等）独立控制。

## 6. 权限校验机制

- **认证中间件**：`auth_middleware`（`backend/src/middleware/auth.rs`）完成认证——取 token（`Authorization: Bearer` 或 HttpOnly Cookie `manner_token`）→ 验签 → `typ` 必须为 `access` → jti 不在 `token_blacklist` → 员工存在且 `pwd_version` 与库一致且 `status = 1`；通过后把 Claims 注入请求扩展。
- **`require_permission(permissions, code)`**：比对令牌内权限快照是否包含目标权限码，不含则返回 403（code=40004）。所有需权限的端点均在 handler 入口调用（端点 → 权限码映射见 `API文档.md`）。
- **令牌内权限快照的失效语义**：
  - `pwd_version`：改密/重置密码/首登激活时递增，旧令牌（含 refresh）立即失效（全端踢出）；
  - `status`：账号禁用（`status != 1`）后所有已签发令牌立即失效；
  - 权限变更本身**不撤销令牌**：依赖令牌过期（默认 30 分钟）后刷新换发新快照。

## 7. 安全要点小结

| 要点 | 说明 |
| --- | --- |
| 子集约束阻断提权链 | 授权操作要求新权限 ⊆ 操作者权限，受限管理员无法授予自身没有的权限码 |
| pwd_version 全端失效 | 改密/重置/首登激活后所有已签发令牌立即失效，无需等待过期 |
| 黑名单与 refresh 轮换 | 登出将 access + refresh 双 jti 拉黑；每次刷新轮换旧 refresh |
| 权限快照 30 分钟自动刷新 | access 令牌内权限为签发时快照，过期后经 refresh 由服务端重新查库签发 |
| 防拉黑保护 | `protect_block = 1` 的员工不可被拉黑（400「该用户受保护，无法拉黑」） |

相关表结构见 `数据库设计.md`，令牌与 Cookie 细节见 `加密标准.md`，接口契约见 `API文档.md`。
