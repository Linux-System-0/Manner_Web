# Manner_Web 架构设计

> 本文档描述 Manner_Web 的整体架构：前后端分离形态、统一响应与错误码、后端分层、请求处理链路、前端分层、认证会话、权限模型、上传安全、日志体系与生产部署。
>
> 技术事实以代码为准：后端以 `backend/src/`（路由以 `backend/src/handlers/mod.rs` 为准）、数据库以 `backend/sql/init.sql` 为准、前端以 `frontend/src/` 为准。更详细的端点清单见 [`API文档.md`](API文档.md)，表结构见 [`数据库设计.md`](数据库设计.md)，权限模型见 [`权限系统设计.md`](权限系统设计.md)。

## 1. 总体架构

Manner_Web 是前后端分离的企业内部 Web 管理系统：前端为 SvelteKit 5 构建的**纯 SPA 静态站点**，后端为 Rust(axum) REST API，数据库为 MySQL 8。无 SSR、无服务端模板渲染，前端只通过 JSON API 与后端交互。

```
┌──────────────┐
│   浏览器 SPA  │  SvelteKit 5 纯静态站点（adapter-static，ssr=false）
└──────┬───────┘
       │ HTTP（JSON API + HttpOnly Cookie 会话）
       ▼
┌──────────────────────────────────────────────┐
│  开发环境：Vite Dev Server（:5173）            │
│   · 静态资源由 Vite 提供                        │
│   · 代理 /api、/uploads → http://localhost:8080│
├──────────────────────────────────────────────┤
│  生产环境：Nginx（:443）                       │
│   · 静态托管 frontend/build/（SPA fallback）    │
│   · 反代 /api、/uploads → 127.0.0.1:8080      │
└──────────────────────┬───────────────────────┘
                       ▼
              ┌──────────────────┐
              │ axum REST API    │  监听 127.0.0.1:8080
              │（单一后端进程）    │
              └────────┬─────────┘
                       ▼
              ┌──────────────────┐
              │   MySQL 8        │  utf8mb4 / InnoDB
              └──────────────────┘
```

各组成部分职责：

| 组件 | 职责 |
| --- | --- |
| 浏览器 | 加载静态 SPA；调用 `/api/*`；以 HttpOnly Cookie（`manner_token` / `manner_refresh`）维持会话；`<img>` 等标签加载 `/uploads/*` 静态文件（同源自动携带 Cookie） |
| Nginx（生产） | 静态托管 + SPA 回退；`/api`、`/uploads` 反代到 `127.0.0.1:8080`；TLS 终止、静态资源长缓存、安全响应头（模板见 `nginx-prod.conf.example`） |
| Vite Dev Server（开发） | 提供前端热更新；代理 `/api`、`/uploads` 到 `http://localhost:8080`，前后端联调免 CORS 配置 |
| 前端 SPA | SvelteKit 5 纯客户端渲染（`adapter-static`，`fallback: 'index.html'`，`+layout.ts` 中 `ssr=false`、`prerender=false`）；无运行时依赖，UI 组件全部自研于 `src/lib/components/` |
| 后端 API | axum 0.7 单进程 REST API；统一响应 `{code, message, data}`；中间件链提供认证、限流、安全加固与日志 |
| MySQL 8 | 唯一持久化存储；9 张表；启动时由后端自动执行 `init.sql` 迁移 |

部署形态（生产）：

```
Nginx :443 ──► 静态文件 frontend/build/（SPA fallback 到 index.html）
         └──► /api、/uploads 反代 ──► 后端进程 127.0.0.1:8080 ──► MySQL 8
```

## 2. 统一响应与错误码

所有接口（含错误响应）统一返回 JSON：

```json
{ "code": 0, "message": "ok", "data": { } }
```

- `code=0` 表示成功；成功时 `data` 携带业务数据（无数据时用 `message` 说明，如「保存成功」）。
- 错误时 `data=null`，`message` 为人类可读的中文说明。
- 成功响应 HTTP 一律为 200（`ApiResponse::ok` / `ok_msg` / `created` 均为 `code=0`，无 201）。
- 业务错误码与 HTTP 状态映射由 `backend/src/error.rs` 的 `IntoResponse` 统一实现：

| code | HTTP | 含义 |
| --- | --- | --- |
| 0 | 200 | 成功 |
| 40000 | 400 | 参数错误（含 422/文本 400/415 由 `harden_response_middleware` 收敛而来） |
| 40001 | 401 | 用户名或密码错误（登录/首登/预检统一，不区分账号不存在/禁用） |
| 40002 | 401 | Token 无效或已过期 |
| 40003 | 401 | Token 已被注销（黑名单） |
| 40004 | 403 | 无权限访问 |
| 40005 | 400 | 校验失败 |
| 40006 | 404 | 资源不存在 |
| 40007 | 409 | 用户名已存在 |
| 40008 | 400 | 旧密码错误 |
| 40009 | 429 | 请求过于频繁（响应携带 `Retry-After` 头） |
| 50000 | 500 | 服务器内部错误 |

## 3. 后端分层

后端代码位于 `backend/src/`，按职责分层：

| 层 | 目录/文件 | 职责 |
| --- | --- | --- |
| 入口 | `main.rs` | 启动流程：`dotenvy` → `Config::from_env` → `init_logging` → `security_warnings` → `init_pool` → `run_migrations(init.sql)` → 生成登录假 bcrypt 哈希 → 构造 `LoginThrottle` → `AppState` → `build_router` → `StripAllowMakeService` → `axum::serve` |
| 配置 | `config.rs` | `Config::from_env()` 读取全部环境变量；`security_warnings()` 输出安全配置告警 |
| 数据库 | `db.rs` | `init_pool`：MySQL 连接池（sqlx `MySqlPoolOptions`，max 20 / min 5） |
| 错误 | `error.rs` | `AppError` 枚举 + `IntoResponse`（错误码 → HTTP 状态映射） |
| 处理器 | `handlers/` | `mod.rs`（`build_router` 路由装配）+ `auth.rs` / `employee.rs` / `chat.rs` / `department.rs` / `system.rs` 五个业务模块 |
| 中间件 | `middleware/` | `auth.rs`（`auth_middleware`、`AuthUser`/`JwtClaims` 提取器、`require_permission`）、`ratelimit.rs`（`LoginThrottle`）、`security.rs`（访问日志、安全加固）、`strip_allow.rs`（剥离 `Allow` 头） |
| 模型 | `models/employee.rs` | 请求/响应结构体（`Employee`、`LoginRequest`、`EmployeeListParams`、`Permission` 等） |
| 服务 | `services/auth.rs` | `hash_password` / `verify_password` / `generate_random_password`（含单元测试） |
| 工具 | `utils/jwt.rs`、`utils/response.rs` | JWT 签发与校验（`Claims`）、统一响应（`ApiResponse<T>`） |

分层约定：

- handler 只做参数解析、权限校验、业务编排与响应组装；SQL 直接使用 sqlx **运行时查询**（`query`/`query_as` + `bind`，非编译期宏），通过 `State(state): State<AppState>` 取 `state.pool` 访问数据库。
- 错误统一通过 `?` 向上传播为 `AppError`，由 `error.rs` 映射为统一响应，handler 内不手工拼错误 JSON。
- handlers 有 `auth` / `chat` / `department` / `employee` / `system` 五个模块（部门为树形 CRUD + 成员归属 + 负责人，角色机制已移除、无 `role.rs`）。

## 4. 请求处理链路

请求进入后端后按如下顺序（**外 → 内**）经过各层：

```
StripAllowMakeService（最外层）
  └─► harden_response_middleware（安全头 + 错误收敛）
        └─► request_logging_middleware（访问日志）
              └─► TraceLayer + CORS（白名单 + allow_credentials）
                    └─► 路由层
                          ├─ public_routes（匿名，6 个）
                          ├─ protected_routes（33 个 + auth_middleware）
                          └─ uploads_router（ServeDir + uploads_extension_guard + auth_middleware）
                          └─ fallback：未注册路径统一 401
```

| 阶段 | 处理者 | 作用 |
| --- | --- | --- |
| 1 | `StripAllowMakeService` | 剥离所有响应 `Allow` 头，避免暴露路由/方法指纹 |
| 2 | `harden_response_middleware` | 附加安全响应头（`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Strict-Transport-Security: max-age=31536000; includeSubDomains`、`Referrer-Policy: no-referrer`、`x-permitted-cross-domain-policies: none`）；将 axum 框架级 422 / 纯文本 400 / 415 错误统一收敛为 `40000`（避免泄露 serde/axum 技术栈指纹）；后端不输出 CSP 与自定义 `Server` 头（由前端 dev server 与生产 Nginx 负责） |
| 3 | `request_logging_middleware` | 记录 `method` / `path` / `status` / `duration_ms` 访问日志 |
| 4 | `TraceLayer` + CORS | 请求追踪；CORS 仅放行白名单来源（`CORS_ALLOWED_ORIGINS`，`allow_credentials(true)`，方法 `GET/POST/PUT/DELETE/OPTIONS`，头 `Content-Type/Accept/Authorization/X-CSRF-Token`） |
| 5 | 路由层 | 匹配 `/api/*` 与 `/uploads/*`（见下） |
| 6 | fallback | 未注册路径统一返回 401（`code=40002`），消除「路由已注册 401 vs 未注册 404」的响应码差分信号 |

路由层细分：

- **public_routes（匿名，6 个）**：`POST /api/auth/login`、`register`、`precheck`、`first-login`、`refresh`，`GET /api/system/login-page`。
- **protected_routes（33 个）**：全部叠加 `auth_middleware`（Bearer 或 Cookie 取 token → 验签 → `typ` 必须为 `access` → 黑名单检查 → `pwd_version`/`status` 校验）；具体端点与权限要求见 [`API文档.md`](API文档.md)。
- **uploads_router**：`GET /uploads/*` 由 `ServeDir` 提供，叠加 `uploads_extension_guard`（聊天子目录 404、扩展名/软链接/引用校验、非图片强制下载）与 `auth_middleware`（**需登录**），详见第 9 节。

## 6. API 客户端要点

`frontend/src/lib/api/client.ts` 是所有请求的唯一出口，关键行为：

| 要点 | 说明 |
| --- | --- |
| `/api` 前缀补全 | 传入 `client.get('/employees')` 自动请求 `/api/employees` |
| 凭据 | `credentials: 'include'`，依赖 HttpOnly Cookie（`manner_token`），JWT 不落 `localStorage`（`manner-auth-storage` 仅存 user 信息、权限不落盘） |
| 超时 | 30 秒超时 |
| 401 并发去重刷新 | 多个请求同时 401 时只发起一次 `POST /api/auth/refresh`，其余请求排队等待后**重放** |
| 刷新失败 | 自动 `logout` 并跳转 `/login`；`skipAuthRedirect` 可跳过；`AUTH_ENDPOINTS`（`/auth/login`、`/auth/first-login`、`/auth/refresh`）不触发刷新重试 |
| 响应处理 | 统一按 `{code, message, data}` 解包，`code !== 0` 抛错并展示 `message` |

## 7. 认证会话架构

### 7.1 JWT 双令牌

| 令牌 | 有效期 | 用途 |
| --- | --- | --- |
| access（`typ="access"`） | `TOKEN_EXPIRE_MINUTES`，默认 30 分钟 | 调用受保护接口；内嵌权限码快照 |
| refresh（`typ="refresh"`） | `REFRESH_TOKEN_EXPIRE_DAYS`，默认 7 天 | 仅 `POST /api/auth/refresh` 换取新 access；签发新 access 时权限**重新查库**，避免快照过期 |

`Claims` 字段（`backend/src/utils/jwt.rs`）：

| 字段 | 说明 |
| --- | --- |
| `sub` | 员工 id |
| `username` / `name` | 用户名 / 姓名 |
| `permissions` | 权限码列表（仅 access 令牌携带；refresh 为空） |
| `exp` | 过期时间戳 |
| `jti` | 令牌唯一 id（黑名单/轮换依据） |
| `pwd_version` | 令牌版本号，与 `employees.pwd_version` 比对 |
| `typ` | `"access"` / `"refresh"`，防身份混淆 |

### 7.2 Cookie 会话

| Cookie | 内容 | 属性 |
| --- | --- | --- |
| `manner_token` | access 令牌 | `HttpOnly; SameSite=Strict; Path=/; Max-Age=…`；`COOKIE_SECURE=true` 时追加 `Secure` |
| `manner_refresh` | refresh 令牌 | 同上 |
| `manner_csrf` | CSRF 双提交令牌（随机 UUID） | `SameSite=Strict; Path=/; Max-Age=…`；**非 HttpOnly**（前端 JS 读取后经 `X-CSRF-Token` 头回传） |

- 令牌来源双通道：优先 `Authorization: Bearer <token>`（API 客户端），回退到 Cookie `manner_token`（浏览器）。
- 登出（`POST /api/auth/logout`）：access + refresh 的 `jti` 同时写入 `token_blacklist`，并清除 Cookie。

### 7.3 校验链与失效机制

`auth_middleware` 校验顺序：取 token → 验签 → `typ` 必须为 `access`（refresh 冒充 access 拒绝）→ `jti` 不在黑名单 → 员工存在且 `pwd_version` 与库一致且 `status=1`。任一失败返回对应 401（`40002`/`40003`）。

| 场景 | 机制 |
| --- | --- |
| 登出 | 双令牌 `jti` 入黑名单 |
| refresh 轮换（F-22） | 每次使用 refresh 换新时旧 `jti` 入黑名单，refresh 令牌单次有效 |
| 改密/重置密码/首登激活 | `pwd_version` 递增 → 全部已签发令牌立即失效（全端踢出） |
| 账号禁用/离职（`status!=1`） | 已签发令牌立即失效 |
| 登录防枚举（F-01） | 启动时生成与 `BCRYPT_COST` 同开销的假 bcrypt 哈希 `login_dummy_hash`；「用户名不存在」分支执行等开销假校验；`precheck` 的假校验在 SQL 之前统一执行 |
| 登录限流（F-02） | `LoginThrottle` 按「(真实 IP, 用户名) 组合键」+「单 IP 失败总数」双维度计数，默认 5 次 / 900 秒，超限返回 429（`40009` + `Retry-After`）；作用于 `login` / `precheck` / `first_login`；阈值可由系统设置动态调整（`update_limits` 清空计数）；登录成功清除该组合与该 IP 的计数；**无全局锁**（防全站/定向账号锁定 DoS 放大） |

### 7.4 密码与登录流程

- 密码 bcrypt 存储（cost 12，`BCRYPT_COST` 可调）；前端明文 HTTPS 传输、**无预哈希**；新密码/改密 **8~72 字节**（`validate_password_strength` 统一校验）。
- 新员工初始密码为 `generate_random_password()` 生成的 16 位字母数字（约 95bit 熵），配合 `must_change_password=1` 强制首登改密。
- 三步登录：`precheck`（返回 `must_change: bool`，仅待激活状态为 true）→ 密码登录，或 `first-login`（校验初始密码 + 设置新密码 8~72 字节 + 自动签发会话；各失败分支执行等开销 bcrypt 假校验防时序枚举）。

## 8. 权限架构概要

- **员工级直接授权**：权限只经 `employee_permissions` 表（员工 ↔ 权限 多对多）直接授予。**RBAC 角色机制已移除**——不存在角色表、角色绑定，也没有部门数据范围。
- 权限码内嵌 access 令牌：签发时查库取员工全部权限码（`permissions p INNER JOIN employee_permissions ep … WHERE ep.employee_id=?`），端点校验不额外查库。
- 端点级校验：handler 内调用 `require_permission(&auth.permissions, "employee:edit")?`，无权限返回 403（`code=40004`）。
- **首个管理员**：全新部署时 `POST /api/auth/register`（匿名）可用，条件是 `system_settings.registration_open='1'` 且 `employees` 表无任何记录；事务内 `SELECT … FOR UPDATE` 防并发抢注；成功后自动授予**全部权限**并将 `registration_open` 置 `'0'`。已有账号后注册一律 403。
- 授权操作（`PUT /api/employees/:id/permissions`，需 `employee:edit`）：覆盖式更新（事务内 DELETE 全量重插）；**新权限必须是操作者自身权限的子集**（防提权）；不能修改自己的权限。
- **防拉黑保护**（`protect_block=1`）：仅表示该员工不可被他人拉黑（聊天侧兜底），不影响删除、更新、重置密码、修改权限等管理操作；由 `chat:protect_block` 权限控制开关。

当前共 **11 个权限码**（9 张表、39 个 API 路由，详见 [`权限系统设计.md`](权限系统设计.md) 与 [`API文档.md`](API文档.md)）：

| 模块 | 权限码 |
| --- | --- |
| employee | `employee:list`、`employee:view`、`employee:create`、`employee:edit`、`employee:delete`、`employee:password` |
| chat | `chat:protect_block`、`chat:group_create`、`chat:upload` |
| system | `system:config`、`system:settings` |

> 注：`system:config`、`chat:group_create` 存在于权限种子中，当前无任何端点校验它们（保留）。其余聊天接口（会话/消息/拉黑/名单/群管理）仅需登录。

## 9. 上传安全

两个上传端点（均受 `DefaultBodyLimit` 100MB 硬限制，multipart 字段名 `file`）：

| 端点 | 权限 | 用途 | 校验 | 存储位置 |
| --- | --- | --- | --- | --- |
| `POST /api/upload` | 登录即可 | 图片（头像等） | 扩展名白名单（png/jpg/jpeg/gif/webp/bmp/ico）+ **魔数校验** | `UPLOAD_DIR` 根目录，`{uuid}.{ext}` |
| `POST /api/upload/file` | `chat:upload` | 任意文件（聊天附件） | 扩展名须为 ASCII 字母数字、非空、≤16 字符；图片类仍魔数校验 | `UPLOAD_DIR/chat/` 子目录，`{uuid}.{ext}` |

安全措施（F-04/F-10/F-24/F-25/F-25b）：

| 措施 | 说明 |
| --- | --- |
| 魔数校验 | PNG `89504E47` / JPEG `FFD8FF` / GIF `GIF8` / WEBP `RIFF…WEBP` / BMP `BM` / ICO `00000100`；不符返回 400「文件内容与声明类型不符」 |
| UUID 重命名 | 落盘文件名一律 `{uuid}.{ext}`，杜绝路径穿越与原名覆盖 |
| 聊天子目录隔离 | 聊天文件存 `uploads/chat/`，`GET /uploads/chat/*` 一律 404；只能经 `GET /api/chat/file/:name`（会话成员校验）下载 |
| 静态访问需登录 | `GET /uploads/*` 叠加 `auth_middleware`，未登录一律 401 |
| 引用校验 | 静态文件必须被 `employees.avatar` 或 `messages.file_url` 引用，否则 404（杜绝硬链接/孤儿文件直读） |
| 软链接拦截 | 路径任一级为软链接 → 404（防符号链接逃逸） |
| 非图片强制下载 | 非图片扩展名响应强制 `Content-Disposition: attachment`，浏览器不内联渲染（配合 `nosniff` 双重兜底） |
| 大小限制 | `DefaultBodyLimit` 100MB 硬限制 + 系统设置 `chat_upload_limit`（`禁止` / `无限制` / 数字+单位 B\|KB\|MB\|GB\|TB） |

## 10. 日志体系

| 日志 | 实现 | 说明 |
| --- | --- | --- |
| 访问日志 | `request_logging_middleware`（`backend/src/middleware/security.rs`） | 每个请求记录 `method` / `path` / `status` / `duration_ms` |
| 业务日志 | `append_log`（`backend/src/handlers/auth.rs`，写入 `LOG_FILE`，默认 `./logs/manner.log`） | 上传成功/失败、权限变更、设置变更等关键业务事件；由 `GET /api/system/logs`（需 `system:settings`）在线查看（`lines` 默认 200，返回 `{lines[], total, file}`） |
| 运行日志 | `tracing` + `tracing-subscriber` | `PROFILE=production` 时输出 **JSON 格式 + 每日滚动**（`logs/manner.log`，`tracing-appender` non_blocking 写盘）；否则终端格式；级别由 `LOG_LEVEL`（默认 debug）控制，`RUST_LOG` 优先 |

## 11. 生产部署形态

- 拓扑：Nginx（443，TLS）→ 静态托管 `frontend/build/`（SPA 回退到 `index.html`）+ `/api`、`/uploads` 反代到 `127.0.0.1:8080`；后端二进制监听回环地址；MySQL 独立部署。
- 前端产物：`cd frontend && npm install && npm run build` → `frontend/build/`（约 70 个文件）；npm/Node 仅构建期需要。
- Nginx 配置模板见 `nginx-prod.conf.example`（替换 `<your-domain>` 与证书路径；含 SPA 回退、静态长缓存、安全响应头、`client_max_body_size 100m`、反代配置）。
- 后端生产：`cargo build --release`，监听 `127.0.0.1:8080`；环境变量经 systemd `Environment=` / Docker `-e` / K8s Secret 注入，`.env` 不入库。

生产关键配置：

| 配置 | 要求 |
| --- | --- |
| `COOKIE_SECURE=true` | HTTPS 环境下必须开启，Cookie 追加 `Secure`；非本机绑定且未开启时启动告警 |
| `JWT_SECRET` | 强随机、≥64 字符；为公开默认值时**拒绝启动**；长度 <32 时启动告警 |
| `CORS_ALLOWED_ORIGINS` | 生产填 `https://<your-domain>`（禁止 `*`，含 `*` 告警） |
| `SERVER_HOST=127.0.0.1` | 绑定 0.0.0.0 会告警；由 Nginx 反代 |
| `TRUSTED_PROXIES` | 经 Nginx 反代部署时填 `127.0.0.1`（可信代理白名单，支持 CIDR）；使登录限流/审计按真实来源 IP 计数，避免失败计数全站共享 |
| `PROFILE=production` | JSON 滚动日志；`LOG_LEVEL=info` |

更新前端时重新 build 覆盖 `dist/` 即可，无需重启 Nginx 与后端。
